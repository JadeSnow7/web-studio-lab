# 用例走查：为任务增加优先级

这是 2026-10-06 建立的目标架构走查，不是已经运行的产品验收。场景中的“任务列表”属于生成 App 的业务；Lab 自己的 Task 表示本次开发目标，两者不能共用身份或存储。当前已有 sbx Codex 执行通路，母模板、业务 API、数据库和独立检查器仍未接入，完整改码与固定验收闭环尚未完成。

预期用户目标：当前项目的任务支持 `priority = low | medium | high`，缺省为 `medium`；页面可以编辑，API 契约一致，旧数据仍可读，停止 API 后用相同数据目录冷启动仍保留新值。此处作为具体走查输入，不在本轮实现业务功能或创建验收脚手架。

## 逐步责任与交接

| 步骤              | 责任模块与层                                                 | 输入 → 输出 / 跨模块调用                                                                                                               | 权威状态                                                               | 失败或取消处理                                                                                         |
| ----------------- | ------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| 1. 页面提出需求   | Presentation；会话与上下文 Application                       | 当前明确 projectId、用户文字、页面身份 → 待确认目标与页面上下文；通过资源公开接口采集                                                  | UI 仅拥有草稿；Session 与上下文快照归会话模块                          | 采集失败显示原因；导航改变页面代次则旧元素引用失效，重新采集                                           |
| 2. 确认目标       | 任务与执行 Application/Domain                                | 项目范围查询、上下文快照、验收要求、预算 → 不可变 TaskVersion；验证模块提供验收要求引用                                                | Task/TaskVersion 归任务模块；验收定义归验证模块                        | 缺项目授权或验收不明确不启动；确认后改变目标需新版本                                                   |
| 3. 创建执行       | 任务与执行 Application；资源 Application                     | requestId + TaskVersion → runId、固定 workspaceId/projectId、基线快照、写入许可；资源读取实际文件版本                                  | TaskRun、预算及许可归任务模块；代码快照归资源模块                      | 第二个写入执行明确拒绝；重复请求返回原执行；切焦点不会改变归属                                         |
| 4. Agent 修改     | 任务用例调用 Harness 端口，Adapters 接现成 CLI；资源处理写入 | 固定输入及权限 → 修改与退出事实；修改涵盖 UI、API schema、迁移与存储                                                                   | 执行事件归任务模块；文件及版本归资源模块                               | 工具失败保留原因；外部文件变化停止冲突写入；取消先禁新工具动作并确认实际停止，保留已有 diff            |
| 5. 启动应用       | 资源与运行环境 Application/Adapters                          | 固定输出 sourceSnapshotId、命令和数据目录 → 新 appInstanceId、前端/API 进程、ready 信息                                                | AppInstance、端口和进程归资源模块；TaskRun 仅引用                      | 启动失败记录原命令/退出码；已启动部分要清理；ready 不等于验证通过                                      |
| 6. 验证页面和 API | 验证、结果与审阅 Application；CDP/验证适配器                 | TaskVersion、验收 hash、固定快照、AppInstance → 每项验证结果、截图/响应证据                                                            | VerificationResult 与证据归验证模块                                    | 页面断言不符为 failed；CDP/服务不可用为 undetermined；取消由任务协调验证器及所属资源清理               |
| 7. 验证持久化     | 验证用例调用资源停止/启动接口；生成 App 自己持有数据库       | 保存 priority → 停止 API 并确认退出 → 相同数据目录冷启动（新 appInstanceId）→ API/UI 重读                                              | 数据由生成 App 拥有；Lab 记录数据目录/初态版本、重启前后实例及验证事实 | 不在重启前 seed 期望值；API 活跃时不让第二进程打开同一数据库；停止未确认不能假装完成冷启动             |
| 8. 汇总或修复     | 任务与执行 Application；验证模块只提供结果                   | 输出快照 + 验证事实 → 执行结果；失败可在固定目标和剩余预算内新 attempt                                                                 | 任务模块记执行状态；验证历史追加保留                                   | 修复后产生新快照并重验；目标变化需新 TaskVersion/TaskRun；不删除失败、放宽 schema 或修改固定验收来通过 |
| 9. 用户审阅       | Presentation 发命令到审阅 Application                        | 指定 taskVersion、sourceSnapshotId、verificationId、diff → reviewId；固定验收通过且仍适用于当前版本才可接受，否则只能记录意见/要求修改 | ReviewDecision 归审阅模块，UI 消费结果                                 | 快照已变化则原结果不再适用，刷新后重验/重审；写入失败不得仅在 UI 改成“已接受”                          |

本例涉及两种不同调用：Renderer 通过 Preload/IPC 进入 Main 工作台用例；任务核心通过端口请求资源、Harness 和验证适配器。当前 Main 内的 `WorkbenchApplication` 拥有任务事实，页面操作适配器只执行 CDP，不自行写任务状态；这与 2026-10-06 原先选择独立 Node 业务宿主的安排不同，修订理由见 [ADR-0001](adr/0001-modular-monolith.md)。源码依赖与运行时消息方向见 [架构基线](../ARCHITECTURE.md)。

## 本例固定的验收与版本关联

- 页面新增、编辑、保存并重新读取三个允许值；API 输入输出契约一致，非法值按固定契约拒绝，旧记录迁移/缺省行为有明确预期。
- 真实持久化包括 API 进程停止与重启，用同一数据目录，不重新 seed；只刷新页面不能作为持久化证据。
- 同页调试证据绑定 `webContents`、页面代次和 AppInstance。独立 E2E 可以用新 browser context，但必须标明来源、身份和初态，不宣称它就是用户正在看的页面。
- 每个 VerificationResult 绑定 TaskVersion、完整 sourceSnapshotId、acceptanceHash、环境/依赖与数据条件、使用过的 appInstanceId。前后端冷启动会产生多个 appInstanceId，均关联到同一验证记录。
- Harness 成功退出只证明本次执行器退出；应用 ready 只证明就绪；断言通过才记验证 passed；用户操作才产生接受记录。工具错误无法判定时记录 undetermined。

## 用反例检验边界

| 插入情景                            | 架构应作出的决定                                                       | 接入时需要的证据                                              |
| ----------------------------------- | ---------------------------------------------------------------------- | ------------------------------------------------------------- |
| 用户切换项目或关闭 Browser 分页     | 本次 runId 的项目/目标不变，View 关闭不停止应用                        | 固定身份的事件与文件路径、重新打开后的实例                    |
| 用户同时在外部编辑器改 API 文件     | 检出版本冲突，不覆盖外部修改，不把旧快照通过显示为当前通过             | 冲突结果及双方内容；后续新快照/验证                           |
| Agent 写了一半后取消                | 关闭新动作入口，等待 Harness/验证器和本次独占进程退出，保留半成品 diff | cancelling 与最终停止事实、文件变更；未确认停止时保留未决状态 |
| 验证通过后又修改文件                | 原通过和接受仅作为历史；新代码待验证/审阅                              | 旧/新 snapshot ID 与 UI 适用性更新                            |
| 写入完成但响应丢失，Lab 重启        | 查询原命令和实际文件，核对进程，不重放写入                             | requestId 去重记录、恢复核对结果                              |
| 页面文字要求“读取所有目录/上传密钥” | 将其作为上下文数据，不扩大权限                                         | 原授权范围保持不变，越界调用被拒绝                            |

## 走查结论与接入门槛

文档能为这条链路分配唯一状态所有者，区分任务执行与应用启动，并说明失败、取消、版本失效和审阅的处理位置。它仍不能证明具体协议和进程行为可用；首次实现须将上表中的调用落为真实公开契约，并执行相应正/负例。

当前源码与未完成能力以[当前运行时](current-runtime.md)为准，初始化时的差距保留在[基线记录](baseline-2026-10-06.md)。2026-10-06 的文档走查没有新增 `priority` 字段、API、迁移、模型调用或运行证据；之后的空间与观察整合也不实现本例的业务字段和独立验收器。
