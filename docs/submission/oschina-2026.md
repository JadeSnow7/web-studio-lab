## 从已有游戏到可核对的修改

开发者选择兼容魔塔工程的本地目录，先看文件预览，再确认复制到运行环境。游戏与编辑器由同一个 App 管理，可以在工作台中打开。AI 按用户明确提供的路线操作游戏，普通新局最终到达 MT4 `(11,10)`，HP 为 926、金币为 7。随后开发者额外授权放置幸运金币，AI 将一楼 `(6,10)` 的空格从 `0` 改为 `53`，重开新局走同一路线，终点与 HP 相同，金币为 14。[E02](oschina-2026-evidence.md#e02)

84 秒成片已经完成。该录像对应 build04，普通轮和金币轮分别有 58、61 条工具调用回执，各有 12 个有序检查点；视频交付记录与独立 model03 验收分开保存。model03 对应 build03，调用数为 59、61，不能混为同一轮。[E03](oschina-2026-evidence.md#e03)

这里验证的是一种兼容工程的受限接入与修改，不是任意项目导入，也不是 AI 自主规划路线。魔塔 AI 只获得四类专用工具；地图修改只允许一楼空格变为幸运金币。视频差异卡由本次实际前后文件计算，不是标准任务页的 Agent 源码 diff。第二轮开局和拾币时画面停留在 Agent 页，动作由工具回执确认，未拍到拾币动画。

## 从标准模板生成可保存的手帐

第二个场景从新的标准 App 开始。开发者提出生成手帐的目标，同时确认项目范围和验收条件；真实 AI 修改页面与接口，工作台构建并启动应用，数据由模板中的 PGlite 本地保存。[E04](oschina-2026-evidence.md#e04)

完整 v5 彩排已经走通生成、新搜索、3 个公开正文来源的读取、显式纳入、AI 正常 UI 保存和刷新核对。它经历了未绑定目标的取消、重新确认以及保存失败后的续跑；从准备到资源退出共 41 分 8.045 秒，包含人工操作、锁屏停顿和收尾。这个耗时不是纯模型时间，也不是一次无干预成功率。[E05](oschina-2026-evidence.md#e05)

正式录制与彩排使用不同项目。生成阶段耗时 7 分 48.008 秒，生成后通过键盘 UI 保存测试内容并刷新核对；两次鼠标定位失败保留。测试文字随后经 UI 清空，但仍有一条空记录。17 日正式研究、AI 保存及独立刷新验收通过，录屏却因窗口 metadata 校验失败而中止，具体失败字段及原因未确认，没有可用视频。因此在原先空白的 18 日重新执行并补录，保留 17 日记录。[E06](oschina-2026-evidence.md#e06)

18 日新运行耗时 1 分 43.280 秒，重新搜索、读取并纳入已知 HSLY 来源，由 AI 正常 UI 填写、按 Enter 保存，再刷新重开；人工独立刷新与只读 GET 确认四字段一致，17 日记录未变。最终手帐成片为 130 秒，前 50 秒生成、后 80 秒研究保存；完整解码和 32 张样帧检查通过。七段补录原片共 366.09 秒，分段之间有间隔，成片经过节选和加速，不能理解为 130 秒连续完成全部任务。[E08](oschina-2026-evidence.md#e08)

研究过程区分“搜索完成”“正文读取成功”和“显式纳入”。本次搜索日志没有候选 URL 列表，无法证明某个正文 URL 来自哪次搜索。来源是重新读取的已知商业资料，不能称本轮搜索新发现或官方核验。Wikivoyage 的回执校验缺陷、17 日的 UNESCO HTTP 403 和保存刷新后一次快捷键失败均保留；18 日运行无失败也不抹去这些历史。

## 工程上怎样组织这条路径

浏览器页面、终端、项目文件和会话共处一个空间，任务明确绑定项目与运行目标。Electron Main 管理工作台事实和授权，renderer 展示状态，独立服务连接 guest Codex、PTY 与工具。标准 App 使用 React、TypeScript、Vite、Hono、Drizzle/PGlite 和 Zod；外部工程通过限定 profile 接入。[E07](oschina-2026-evidence.md#e07)

这种组织方式便于追踪“在哪个项目上做了什么、结果如何”：运行、检查和人工接受分别记录；关闭页面不等于停止 App；发现版本冲突或清理未确认时保留问题状态。受限魔塔工具通过真实页面输入和带预期散列的地图写入工作，手帐则使用标准 App 的页面与数据能力。

SSH、多会话及其他资源 Provider 有源码入口和历史记录，本次两段演示没有逐项覆盖。它们不是本次场景验收的新增结论。模型路线通过也不证明强 OS 沙箱隔离；相关探针未成功执行到隔离验证阶段。完整比赛 priority 业务 API、独立检查器和报告闭环仍有缺口，不能把工具回执当成所有固定验收均已通过。

## 如何运行与复现

验证环境为 macOS Apple Silicon，项目要求 Node 24、pnpm 10.34.6。先按[根 README](../../README.md)和[依赖说明](../development/dependencies.md)准备依赖；真实 AI 与终端还需要已配置的 sbx、guest Codex、认证和网络。新机器需重新检查，不复制私有 profile 或凭据。源码命令如下，本文编写期间未执行这些命令：

```sh
pnpm install --frozen-lockfile
WSL_SBX_NAME='<已准备的沙箱名称>' pnpm dev
```

复现新增场景时，应使用[PR 整合记录](../acceptance/submission-20261016/README.md)登记的候选 commit，不能只检出基线提交；本材料记录实现提交的本地回归，推送及 validate-only 状态以对应 Draft PR 回执为准，不称已发布发行版。操作步骤、前置条件、证据留存和人工介入说明见[演示与复现说明](demo-guide.md)。真实模型、窗口验证、录像和本次 PR 回归均按各自版本判断；新候选的离线检查不替代历史真实运行。
